# ТЗ: мобильное приложение «Учёт расходов на авто» (финальная версия)

> Документ для разработки приложения через Claude Code. Написан так, чтобы
> человек без опыта мог давать его частями и понимать каждый пункт.
> Все ключевые решения зафиксированы. Версия от 30.05.2026 (v3, добавлен
> Этап 10: финальный редизайн дашборда и навигации).

---

## 1. Что это и для кого

Личное приложение для учёта всех расходов на одну машину: заправки, прочие
траты, обслуживание (масло, мойка, дворники, гос. техосмотр). Приложение само
считает цену литра, расход топлива и напоминает о сроках обслуживания.

Главные принципы:
- **Минимализм.** Один экран — одна задача. Никаких лишних полей.
- **Минимум ручного ввода.** Что можно посчитать — считается само.
- **Одна машина.** Без гаража, без переключения между авто.
- **Работает офлайн.** Все данные на телефоне, интернет не нужен.

---

## 2. Глоссарий (простыми словами)

- **Одометр / пробег** — счётчик километров машины. В приложении это одно
  число, которое растёт со временем.
- **Регламент** — правило обслуживания. Например: «менять масло каждые
  8 000 км». У регламента есть интервал и точка последнего выполнения.
- **Запись** — любое внесённое событие: заправка, расход или выполненное ТО.
- **Таблица** — список однотипных записей в базе данных.
- **Поле** — одно свойство записи (дата, сумма, литры…).
- **PK** (primary key) — уникальный номер записи внутри таблицы.
- **FK** (foreign key) — поле-ссылка на запись в другой таблице.
- **Гос. ТО** — ежегодный визит в госорганы: дорожный налог + страховка +
  технический осмотр. Это НЕ замена масла. Это и категория расхода, и
  ежегодное напоминание по дате.

## 3. Технологический стек

Максимально простой и популярный стек — по нему больше всего примеров, что
важно при работе через Claude Code:

- **React Native + Expo** — фреймворк для мобильных приложений. Expo упрощает
  запуск: тестировать можно прямо на телефоне через приложение Expo Go.
- **SQLite** (через `expo-sqlite`) — локальная база данных на телефоне.
- **expo-notifications** — push-уведомления для напоминаний.

**Платформа: обе (Android + iOS).** Expo поддерживает обе. Важно: для сборки
iOS-версии нужен Mac или платный облачный сервис сборки Expo (EAS Build).
Android собирается без Mac. Рекомендация: разрабатывать и тестировать на обеих
через Expo Go, а финальную iOS-сборку делать через EAS, когда дойдёт до релиза.

**Тёмная тема — ОСНОВНАЯ.** Приложение по умолчанию тёмное (как прототип) и
строится в тёмных цветах с ПЕРВОГО экрана. Цвета берутся из дизайн-системы
(отдельный файл) через объект темы, без хардкода. На Этап 9 откладывается
только: переключатель тем и светлая тема как альтернатива.

- **Локализация (i18n)** — двуязычность RU + EN, закладывается с Этапа 1
  (раздел 6.7).

## 4. Экраны приложения

Внизу — панель с 4 вкладками и кнопкой «+» по центру.

### 4.1. Главная (Дашборд) — стартовый экран
Первое, что видно при открытии. Сверху вниз:
1. Месяц и текущий пробег. В правом верхнем углу — иконка-шестерёнка,
   открывающая экран Настройки (раздел 4.6).
2. Крупно — сумма расходов за текущий месяц (в выбранной валюте).
3. Две карточки: средняя цена литра и средний расход (л/100км). Подпись под
   значением расхода — «л/100км · за всё время» (в две строки): это
   средневзвешенное за ВСЮ историю машины (§6.2), не за окно графика, как на
   Статистике (§4.5) — уточнение добавлено, чтобы не путать два разных числа
   на двух экранах.
4. Список активных напоминаний с цветами статусов (по дизайн-системе):
   - красный `#e5484d` — пора / просрочено;
   - жёлтый `#e0a020` — скоро;
   - зелёный `#4caf7d` — в норме.
   Голубой `#3db5f5` — это обычный акцент (активные элементы), НЕ статус.

### 4.2. История
Список всех записей (заправки + расходы + ТО), отсортирован по дате.
Фильтр по типу и категории. Тап по записи — детали, свайп — удалить/изменить.
В строке расхода иконка берётся из его категории (поле `CATEGORY.icon`, раздел
5.4) — та же иконка, что на плитке категории в форме «Расход»; если категория
удалена или иконка не задана — запасная иконка `receipt-outline`. У заправок
и записей обслуживания — свои фиксированные иконки (капля / гаечный ключ),
без изменений.

### 4.3. Кнопка «+» (добавить)
Приподнята в центре нижней панели (5 вкладок: Home / History / [+] / Reminders /
Stats), голубой градиент. Тап открывает Bottom Sheet (Action Sheet) снизу с
выбором типа: «Заправка», «Расход», «Обслуживание». Заправка — самая частая.

### 4.4. Обслуживание
Список регламентов с полоской прогресса и остатком до срока. История
выполненных работ. Кнопка «Сделано» у каждого регламента — фиксирует
выполнение и обнуляет счётчик. Внизу — «+ Добавить регламент».

### 4.5. Статистика
Переключатель: Топливо / Расходы / Расход (л/100). График трат по месяцам —
по умолчанию окно из 6 месяцев; стрелки `‹ ›` у заголовка периода двигают
выбранный месяц на ±1 (окно подъезжает само, только когда выбор выходит за
его край). Переключатель «За всё время» меняет режим на все месяцы, где есть
данные — суммы, расход и разбивка по категориям считаются по всей истории, а
график становится горизонтально прокручиваемым. Разбивка прочих расходов по
категориям.

Тап по столбику графика выбирает его месяц — то же самое действие, что и
стрелки `‹ ›` (заголовок периода, сумма/расход сверху справа); выбранный
столбик подсвечивается акцентным градиентом, как и текущий месяц по
умолчанию. Область нажатия — вся колонка (столбик на всю высоту графика +
подпись месяца под ним), а не только видимая полоска бара, иначе по
низким/пустым столбцам почти невозможно попасть пальцем. Работает на всех
трёх вкладках. В режиме «За всё время» тап по столбику **отключён** (месяцы
там не выбираются по отдельности — заголовок и сумма уже показывают весь
период; это выбранный, более простой вариант, а не переключение режима
обратно на 6 месяцев с заодно выбором месяца).

На вкладке «Расход (л/100)» столбик каждого месяца — это ДОЛЯ сегментов
(между полными баками), пришедшаяся на этот месяц, а не целый сегмент,
отнесённый к месяцу закрывающей заправки (подробности разбивки — §6.2).
Поэтому длинный отрезок без полного бака внутри (например, два полных бака
с разницей в два месяца) распределяется по месяцам пропорционально пробегу,
и ни один месяц не остаётся пустым только из-за того, что в нём не было
полной заправки. Месяц, в котором сегмент действительно не закрылся (пробег
не оценить — например последний отрезок после самой свежей полной заправки
ещё не закрыт следующей), показывает «—» с подсказкой «Нет закрытого отрезка
между полными заправками». Средний расход «За всё время» и карточка на
главном экране считаются по целым сегментам (как в §6.2) и не зависят от
этой помесячной разбивки — поэтому их значение может не совпадать с простым
усреднением чисел по месяцам (это ожидаемо: сегмент короче месяца или
длиннее месяца не весит в среднем как целый месяц).

Карточка «Средний расход» под графиком (одна из четырёх в сетке 2×2, тап
открывает список заправок) показывает под числом подпись периода: «за май
2026» — конкретный выбранный месяц (через локаль), либо «за всё время», если
включён переключатель. Это то же число, что и «за всё время» на главном
экране, только когда MONTHS = все месяцы с данными (allTime) — иначе это
другой, более короткий период (один месяц), и подпись явно это показывает,
чтобы два похожих числа на двух экранах не путали.

**Карточки под графиком считаются за выбранный месяц, а не за окно графика
(вкладки «Расход л/100» и «Затраты»).** Окно из 6 столбиков — это только
навигация (какие месяцы видно на графике и из чего выбирают стрелками `‹ ›`
или тапом); сами карточки под ним относятся к ОДНОМУ месяцу, который выбран
и показан в шапке — так же, как уже было устроено для суммы сверху справа.
Режим «За всё время» не меняется — там карточки, как и раньше, считаются по
всему периоду (все месяцы с данными сразу).

- **«Расход л/100»** (fuelRepo.getMonthlyFuelConsumption, §6.2): «Средний
  расход» и «Пробег за месяц» (подпись «Пробег за период» заменяется на
  «Пробег за месяц» вне режима «за всё время») — доля выбранного месяца из
  помесячной разбивки сегментов, то же число, что и сумма в шапке. «Минимум»
  / «Максимум» — по отдельным полным заправкам, ЗАКРЫВШИМСЯ в этом месяце
  (не по всему окну); нет такой заправки в месяце → «—», даже если «Средний
  расход» этого месяца не пустой (у него может быть доля сегмента без
  закрывающей заправки именно в этом месяце — это нормально).
- **«Затраты»**: карточки сравнивали МЕСЯЦЫ окна («Средний в месяц», «Всего
  за период», «Минимальный/Максимальный месяц») — в режиме «за всё время»
  это осталось. В режиме месяца сравнивать месяцы друг с другом не имеет
  смысла (выбран один), поэтому карточки теперь сравнивают ОТДЕЛЬНЫЕ траты
  внутри выбранного месяца: «Средний чек», «Всего за месяц» (= сумма в
  шапке), «Минимальная трата», «Максимальная трата» — подписи меняются
  вместе со смыслом.
- **«Заправки»**: там нет карточек 2×2 под графиком (только сумма в шапке и
  «Пробег за месяц» рядом с ней, плюс круговая диаграмма по месяцам окна) —
  сумма уже считалась за выбранный месяц и не менялась этой правкой.

### 4.6. Настройки (Settings)
Открывается шестерёнкой из угла дашборда (НЕ отдельная вкладка — навигация
остаётся 4 вкладки + «+»). Разделы:
- **Машина:** название, текущий пробег, управление категориями (раздел 6.5).
- **Валюта:** выбор из списка (раздел 6.6).
- **Язык:** RU / EN (раздел 6.7).
- **Внешний вид:** переключатель тёмная/светлая тема (Этап 9).
- **Уведомления:** вкл/выкл напоминаний.
- **Резервная копия:** экспорт / импорт файла (раздел 9).

## 5. Структура данных (таблицы и поля)

Семь таблиц. Тип `int` — целое, `float` — дробное, `string` — текст,
`bool` — да/нет, `date` — дата.

### 5.1. CAR — машина (одна запись)
| Поле | Тип | Описание |
|---|---|---|
| id | int PK | номер записи |
| name | string | название («Моя машина») |
| base_odometer | int | базовый пробег, введённый вручную при онбординге/в Настройках — нижняя граница |
| current_odometer | int | текущий пробег, км — производная величина, не вводится напрямую |
| fuel_unit | string | единица топлива («литр») |
| currency | string | код выбранной валюты («MDL», «USD», «EUR»…) — см. раздел 6.6 |

`current_odometer` обновляется автоматически и **двусторонне**: это максимум
из `base_odometer` и пробегов всех заправок, расходов и записей обслуживания.
Пересчёт происходит при каждом добавлении, изменении и удалении любой из этих
записей — поэтому удаление записи с максимальным пробегом опускает
`current_odometer` обратно (а не оставляет задранным), но ниже `base_odometer`
он никогда не опустится.

`currency` хранит КОД валюты (ISO, например `MDL`). Символ для отображения
(`L`, `$`, `€`) берётся из встроенного справочника валют (раздел 6.6).

## 6. Логика и формулы

### 6.1. Цена за литр
```
price_per_liter = total_cost / liters
```
Считается всегда при сохранении заправки. Округлять до 2 знаков.

### 6.2. Расход топлива (л/100км)
Считается **только если бак полный** (`is_full_tank = true`) и есть
предыдущий полный бак. Литры неполных заправок между двумя полными не
пропадают — «копятся» и идут в числитель следующего полного бака:
```
пройдено      = odometer_текущий − odometer_прошлой_полной_заправки
litersВсего   = liters этого полного бака + сумма liters всех неполных
                заправок строго между прошлой полной и текущей
consumption   = litersВсего / пройдено × 100
```
Если бак неполный — `consumption` не считается (поле пустое). Если
предыдущего полного бака нет (первая полная заправка в истории) —
`consumption` тоже пустое.

**Средний расход за период** считается **средневзвешенно**, а не как
простое среднее `consumption` отдельных заправок: вся история разбивается на
сегменты (один сегмент = один полный бак с предыдущим, с его `litersВсего` и
`пройдено`), затем `avg = сумма litersВсего всех сегментов / сумма пройдено
всех сегментов × 100`. Так короткий сегмент-выброс (мало км) не весит в
среднем так же, как обычный длинный сегмент. Минимальный и максимальный
расход периода — по-прежнему по отдельным заправкам, без взвешивания (смысл
этих чисел — «лучшая/худшая заправка», а не средний расход периода).

`consumption` пересчитывается автоматически у всех полных баков машины после
добавления, изменения или удаления любой заправки, а также после импорта
резервной копии (раздел 9) — вручную пересчёт не запускается.

**Расход по месяцам (вкладка «Расход л/100», §4.5).** Раньше весь сегмент
относили к месяцу закрывающей его полной заправки — из-за этого длинный
сегмент (несколько месяцев без полной заправки внутри) целиком попадал в
один месяц, а месяцы без полной заправки оставались пустыми. Теперь каждый
сегмент (от `odometer_o1`/даты `d1` прошлой полной заправки до
`odometer_o2`/даты `d2` текущей) раскладывается по календарным месяцам,
которые он пересекает:
```
для каждого месяца ym в сегменте:
  o_начало = одометр на начало пересечения сегмента с ym (интерполяция)
  o_конец  = одометр на конец пересечения сегмента с ym (интерполяция)
  км(ym)   = o_конец − o_начало
  литры(ym)= км(ym) / пройдено × litersВсего      // та же пропорция, что и км
```
Одометр на промежуточную дату оценивается линейной интерполяцией по датам
между `o1` и `o2`, по всем точкам с известным одометром внутри сегмента
(неполные заправки и расходы с указанным пробегом) — чем их больше, тем
точнее оценка пробега внутри месяца, а не только по двум концам сегмента.
Расход месяца = `сумма литры(ym) / сумма км(ym) × 100`. Сумма км(ym) и
литры(ym) по всем месяцам сегмента всегда равна `пройдено` и `litersВсего`
этого сегмента. Месяц без км в сегментах (например последний отрезок после
самой свежей полной заправки — она ещё не закрыта следующей) — «—».
Среднее «за всё время» и карточка на главном экране эту разбивку не
используют — считаются как и раньше, по целым сегментам.

### 6.3. Движок напоминаний
Для каждого регламента считается «остаток до срока»:

**Если type = mileage (масло):**
```
остаток_км = (last_odometer + interval_km) − current_odometer
```

**Если type = time (Гос. ТО, мойка, дворники):**
```
остаток_дней = (last_date + interval_days) − сегодня
```

Статус по остатку:
- остаток > warn_before → **в норме** (серый/зелёный, тихо);
- 0 < остаток ≤ warn_before → **скоро** (жёлтый, плашка);
- остаток ≤ 0 → **пора** (красный + push-уведомление).

**Push-уведомления — два разных механизма, в зависимости от типа регламента.**

Для `type = time` (Гос. ТО, мойка, дворники) — календарный триггер на 9:00
утра по часовому поясу телефона (`hour: 9, minute: 0`):
- `ok`   → разовый CALENDAR на дату warnDate («скоро») в 9:00;
- `soon` → разовый CALENDAR на дату dueDate («пора») в 9:00;
- `due`  → повторяющийся CALENDAR (`repeats: true`) каждый день в 9:00, пока
  регламент не отметят выполненным.
Если вычисленный момент уже прошёл сегодня — берётся завтрашнее 9:00.
Текст уведомления различает «просрочено» (остаток < 0) и «срок сегодня»
(остаток = 0) — это разные формулировки, не одна общая.

Для `type = mileage` (масло) — немедленный push, **без** календарного
триггера и **без** повтора: пробег сам по себе не растёт между записями
пользователя, ждать 9:00 бессмысленно. Push отправляется один раз в момент,
когда статус ухудшился (`ok → soon`, `soon → due` и т.п.) — сравнение с
`notified_status` регламента (раздел 5.6) не даёт отправить дубликат.
Статус улучшился (например, после «Сделано») — push не шлётся,
`notified_status` тихо сбрасывается, чтобы следующее ухудшение уведомило
снова.

При нажатии «Сделано»:
- создаётся запись в SERVICE_RECORD с датой и пробегом (оба поля
  обязательны, дата не в будущем);
- **пробег записи может быть МЕНЬШЕ текущего `current_odometer` машины** —
  это нормальный случай: форма фиксирует, когда работа была сделана
  ФАКТИЧЕСКИ, часто задним числом (например, «масло поменяли на 206500 км»
  при текущих 211294 км). `current_odometer` при этом не опускается —
  `recalcCurrentOdometer()` (раздел 5.1) берёт максимум по всем записям,
  а не присваивает значение напрямую;
- `last_odometer` и `last_date` регламента — **не вводятся напрямую**, а
  являются производными: берутся из записи SERVICE_RECORD с САМОЙ ПОЗДНЕЙ
  ДАТОЙ среди привязанных к этому регламенту (`reminder_id`) — не с
  наибольшим пробегом: можно задним числом добавить запись с пробегом
  меньше уже существующей, но более позднюю по дате, и именно она станет
  «последней»;
- счётчик начинает отсчёт заново от этих значений.

**Откат при удалении записи.** Если удалить запись SERVICE_RECORD, которая
была последней закрывающей для регламента, — `last_odometer`/`last_date`
пересчитываются на предыдущую по дате запись этого регламента, а если таких
записей больше не осталось — откатываются на `start_odometer`/`start_date`
(раздел 5.6, точка отсчёта регламента). Регламент не остаётся
«выполненным навсегда» после удаления записи, которая это зафиксировала.

**Задать «когда сделано в последний раз» при создании/редактировании
регламента.** Форма регламента (раздел 4.4) не ограничивается вводом только
интервала — для `type = time` там же есть поле «Когда сделано в последний
раз» (дата, по умолчанию сегодня, не в будущем), для `type = mileage` — поля
«Дата последней замены» и «Пробег при последней замене» (по умолчанию
сегодня / текущий пробег машины, но пробег допустимо указать меньше
текущего — опять же задним числом). Значения сохраняются в
`start_date`/`start_odometer`; если у регламента ещё нет ни одной
SERVICE_RECORD, `last_*` сразу пересчитываются от них же (см. откат выше) —
то есть регламент может оказаться «скоро» или даже «пора» сразу после
создания/правки, если пользователь указал достаточно давнюю точку, а не
обязательно стартовать «в норме», как было раньше. Чтобы это не считалось
«переходом статуса» и не вызвало немедленный push по mileage-модели выше,
`notified_status` сразу выставляется в соответствии с только что посчитанным
статусом — push о статусе, который пользователь сам только что ввёл и уже
видит на экране, не отправляется; отправится только о СЛЕДУЮЩЕМ, настоящем
ухудшении.

**«Пробег при последнем выполнении» для `type = time` (необязательное
поле).** Под полем «Когда сделано в последний раз» в форме регламента (для
`type = time`) есть ещё одно поле — пробег, целое число от 0 до текущего
пробега машины. В отличие от одноимённого поля для `type = mileage`, оно
**необязательно**: можно оставить пустым. Это чисто информационное поле —
показывается в карточке регламента и в его деталях как «Last done
(odometer)», но **не участвует** в расчёте остатка/статуса по времени (тот
считается только по `last_date`). Пустое значение сохраняется в то же
`start_odometer`/`last_odometer` как сентинел `NO_ODOMETER = -1`
(`utils/reminders.ts`) — колонка в БД остаётся `NOT NULL INTEGER`, миграция
схемы не понадобилась; на экране сентинел отображается как «—». Как и для
mileage-поля, значение переопределяется первой же реальной записью
SERVICE_RECORD по этому регламенту (откат при удалении — см. выше).

### 6.4. Сумма за месяц (дашборд)
Сложить `total_cost` всех заправок + `amount` всех расходов + `cost` всех
работ обслуживания, где дата попадает в текущий месяц.

### 6.5. Управление категориями
- В сетке выбора категории последняя ячейка — **«+ Добавить категорию»**.
  Форма: название + выбор иконки. Новая категория сохраняется с
  `is_builtin = false`.
- **Редактирование** доступно для любой категории (название, иконка).
- **Удаление:**
  - встроенные категории (`is_builtin = true`) удалять НЕЛЬЗЯ — кнопка
    удаления скрыта/заблокирована;
  - пользовательскую категорию можно удалить, ТОЛЬКО если на неё не ссылается
    ни один расход (категория пустая);
  - если на категорию есть ссылки — удаление запрещено, показать сообщение
    («Сначала удалите или перенесите расходы этой категории»).

### 6.6. Выбор валюты (простой вариант — без конвертации)
- Приложение использует ОДНУ валюту на все суммы. Она хранится в `CAR.currency`
  как код (например `MDL`).
- Конвертации по курсу НЕТ. Числа не пересчитываются — валюта это просто
  ярлык/символ, который показывается рядом с суммами.
- При первом запуске (или в Settings) пользователь выбирает валюту из
  встроенного списка. Экран выбора — со строкой поиска.
- Символ для отображения берётся из справочника валют (см. ниже). Если у
  валюты нет короткого символа — показывается её код.
- Смена валюты меняет только отображение во всём приложении, данные не трогает.

**Встроенный справочник валют** (код → символ → название). Хранится в коде как
заготовленный массив, без интернета:

Топ мировых: USD ($, доллар), EUR (€, евро), GBP (£, фунт).
СНГ и регион: MDL (L, лей), RUB (₽, рубль), UAH (₴, гривна),
KZT (₸, тенге), BYN (Br, бел. рубль), AZN (₼, манат), AMD (֏, драм),
GEL (₾, лари), KGS (сом), TJS (сомони), UZS (сум), TMT (манат).
Дополнительно (по желанию): TRY (₺), PLN (zł), RON (lei).

Список легко расширять — это просто строки в массиве.

### 6.7. Языки интерфейса (RU + EN)
- Приложение двуязычное: русский и английский.
- Все надписи интерфейса хранятся в двух словарях (RU и EN), а НЕ пишутся
  прямо в экранах. Каждый экран обращается к надписи по ключу, библиотека
  подставляет нужный язык. Используется стандартная `i18n`-библиотека
  (например `i18next` / `react-i18next`).
- **Важно для разработки:** двуязычность закладывается с ПЕРВОГО экрана
  (Этап 1), а не прикручивается потом. Каждый новый экран сразу пишется
  через словарь. Хардкод текста в компонентах запрещён.
- Переключатель языка — в Settings.
- Язык по умолчанию при первом запуске: определяется по языку телефона
  (если системный язык русский → RU, иначе → EN). Потом меняется вручную.
- Что переводится: ВСЕ надписи интерфейса (кнопки, заголовки, лейблы,
  статусы напоминаний, сообщения). Названия встроенных категорий тоже
  переводятся (см. таблицу соответствия в разделе 7.1).
- Что НЕ переводится: данные пользователя (его описания расходов, заметки,
  названия созданных им категорий) — они хранятся как есть.

## 9. Резервная копия данных

**Решение: Вариант 1 — экспорт/импорт файла (на старте).**
- Кнопка «Экспорт» сохраняет все данные в один файл. Реализован только
  формат **JSON** (CSV не реализован).
- Файл можно отправить себе в Telegram / на почту / в облако вручную.
- При смене телефона — «Импорт» из этого файла **полностью заменяет**
  текущие данные содержимым файла (старые заправки/расходы/категории/
  регламенты удаляются, новые заливаются как есть). Сразу после импорта
  пробег машины и расход топлива у всех полных баков пересчитываются
  автоматически по тем же правилам, что и при обычном вводе (разделы 5.1,
  6.2) — за одним исключением: `price_per_liter` каждой заправки берётся из
  файла напрямую, без пересчёта (это просто `total_cost / liters`,
  пересчитывать не из чего, кроме тех же чисел из файла).

Плюсы: просто, бесплатно, данные под полным контролем, без регистраций.
Минус: бэкап делается вручную (не автоматически) — для личного приложения
это приемлемо.

**Android: `allowBackup = false`.** Автоматический системный бэкап Android
(который иначе мог бы тихо сохранить и восстановить БД приложения при
переустановке) отключён сознательно: после удаления приложения данные НЕ
возвращаются сами — единственный способ восстановить их — ручной «Импорт»
из файла, экспортированного заранее.

> Примечание: «облака Claude» для хранения данных приложения не существует —
> Claude это инструмент для кода и общения, не бэкенд-сервис. Если позже
> захочется автоматической синхронизации между устройствами, можно добавить
> бесплатный бэкенд Supabase (Вариант 3), но это усложняет проект и требует
> интернета. На старте — не нужно.

## 10. Как вести разработку с Claude Code (пошагово)

Не строить всё сразу. Двигаться маленькими этапами — после каждого проверять,
что приложение запускается.

1. **Этап 0 — окружение.** Установить Node.js и Expo, создать пустой проект,
   запустить на телефоне через Expo Go. Цель: увидеть «Hello world».
2. **Этап 1 — фундамент: база данных + темы + языки + импорт.** Создать
   таблицы (раздел 5, включая APP_SETTINGS) в SQLite. Залить стартовые
   категории и регламенты (раздел 7). Завести объект тёмной темы из
   дизайн-системы (все цвета через него, без хардкода). Настроить i18n со
   словарями RU и EN (раздел 6.7). Написать скрипт импорта старых данных
   (раздел 8). С этого момента: текст — через словарь, цвета — через тему.
3. **Этап 2 — добавление заправки.** Форма + сохранение + автоподсчёт цены
   литра (разделы 4.3, 5.2, 6.1).
4. **Этап 3 — история.** Список всех записей из базы (раздел 4.2).
5. **Этап 4 — дашборд.** Сумма за месяц, цена литра, расход (разделы 4.1, 6.4).
6. **Этап 5 — прочие расходы.** Форма с выбором категории (разделы 4.3, 5.3).
7. **Этап 6 — обслуживание.** Регламенты, остаток до срока, «Сделано»
   (разделы 4.4, 5.6, 6.3).
8. **Этап 7 — напоминания.** Движок статусов + push-уведомления (раздел 6.3).
9. **Этап 8 — статистика.** Графики (раздел 4.5).
10. **Этап 9 — полировка.** Управление категориями (6.5), экран Настроек (4.6),
    светлая тема + переключатель тем, экспорт/импорт (раздел 9),
    удаление/редактирование записей. (Тёмная тема и выбор валюты уже сделаны
    раньше.)
11. **Этап 10 — финальный редизайн дашборда и навигации.** Привести UI в
    соответствие с прототипом из дизайн-системы:
    - 5 вкладок в нижней навигации: Home / History / [+] / Reminders / Stats
      (вкладка регламентов называется «Напоминания»/«Reminders», иконка —
      колокольчик `notifications-outline`; маршрут остался `service.tsx`),
      кнопка «+» приподнята в центре с голубым градиентом.
    - Тап по «+» открывает Action Sheet (Bottom Sheet) с выбором:
      Заправка / Расход / Сервис.
    - Убрать кнопки быстрого доступа (Заправка/Расход/История) с дашборда —
      они теперь в навигации.
    - Карточки напоминаний крупнее, с иконкой типа задачи справа и подсветкой
      активной карточки (статус «пора»).

Каждому этапу давать Claude Code отдельную задачу со ссылкой на нужные разделы.
Например: «Реализуй Этап 2 по разделам 4.3, 5.2 и 6.1».

> Примечание: выбор валюты (6.6) технически очень простой, его можно сделать
> и раньше Этапа 9 — например, сразу после Этапа 1, чтобы суммы с самого
> начала показывались в нужной валюте. Но для импорта старых данных
> (молдавские леи) дефолт `MDL` подойдёт и без отдельного экрана.

## 11. Будущие улучшения (НЕ на старте)

Зафиксировано, чтобы не забыть. Реализовывать позже, когда базовое приложение
работает.

- **Локальное форматирование чисел (Intl).** Разные страны пишут суммы
  по-разному: `1 000,50` против `1,000.50`, символ валюты до или после числа.
  На старте — просто символ рядом с числом, без локализации. Позже можно
  подключить встроенный механизм `Intl.NumberFormat`, который форматирует
  суммы по правилам выбранной страны/локали автоматически.
- **Конвертация валют по курсу.** Если когда-нибудь понадобится вводить траты
  в разных валютах и сводить их в одну — потребуется источник курсов (внешний
  API) и интернет. Сознательно отложено: усложняет офлайн-приложение.
- **Автоматический облачный бэкап / синхронизация между устройствами**
  (Supabase или подобное) — см. раздел 9.
- **Несколько машин (гараж).** Сейчас приложение под одну машину. Структура
  данных это уже допускает (везде есть `car_id`), но UI под выбор машины
  не делается на старте.

## 12. Сводка принятых решений

- Платформа: обе (Android + iOS).
- Масло: по пробегу, 8 000 км, предупреждать за 500 км.
- Гос. ТО: по дате, раз в год, предупреждать за 25 дней (налог + страховка +
  техосмотр).
- Мойка: по дням, каждые 14 дней.
- Дворники: по дате, раз в год от последней замены.
- Импорт старых данных из Google-таблицы: да, скриптом на Этапе 1.
- Темы: тёмная — ОСНОВНАЯ, закладывается с первого экрана через объект темы.
  Светлая тема + переключатель — на Этап 9. Цвета в файле дизайн-системы.
- Цвета статусов: пора/просрочено = красный, скоро = жёлтый, норма = зелёный.
  Голубой `#3db5f5` — обычный акцент, не статус.
- Настройки (Settings): открываются шестерёнкой из угла дашборда, не вкладка.
- Резервная копия: экспорт/импорт файла (Вариант 1).
- Категории добавляются пользователем: да. Встроенные (12) защищены от
  удаления. Пользовательскую можно удалить только если пустая.
- Валюта: одна на приложение, выбор из встроенного списка (топ + СНГ), без
  конвертации по курсу. Хранится код в `CAR.currency`.
- Языки: двуязычно RU + EN через i18n-словари, закладывается с Этапа 1.
  Переключатель в Settings, дефолт по языку телефона. Хардкод текста запрещён.
- Отложено на будущее (раздел 12): локальное форматирование чисел (Intl),
  конвертация валют, облачный бэкап, несколько машин.
- Этап 10 (финальный редизайн): 5 вкладок с приподнятой «+» по центру,
  Action Sheet для выбора типа записи, карточки напоминаний с иконками типа,
  убраны дублирующие кнопки с дашборда.
