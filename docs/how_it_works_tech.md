## 1. Расход топлива для одной заправки (§6.2)

**Формула — одна функция:** `calcConsumption()` в `db/repositories/fuel.ts`.
И пересчёт в БД (`recalcAllFullTankConsumption()`), и живое превью в форме
(`app/add-fuel.tsx`) вызывают именно её — формула существует только в одном
месте и не может разойтись между превью и сохранённым значением.

`consumption` больше не считается разово в момент вставки (как было раньше
в `addFuelEntry()`). Вместо этого после **каждого** изменения заправок —
`addFuelEntry()`, `updateFuelEntry()`, `deleteFuelEntry()` (все три —
`db/repositories/fuel.ts`) — вызывается `recalcAllFullTankConsumption()`,
которая пересчитывает `consumption` у **всех** полных баков машины с нуля.
Это и есть автоматический пересчёт, который требовался: правка старой
записи или её удаление больше не оставляет `consumption` у соседей
устаревшим.

### Когда расход считается

Только если **одновременно**:
1. `is_full_tank === 1` (бак отмечен как полный) — иначе `consumption = null`, безусловно.
2. Есть **предыдущий полный бак** — ищет `getPrevFullTank(carId, odometer, excludeId?)`
   (`fuel.ts`):
   ```sql
   SELECT * FROM fuel_entry
    WHERE car_id = ? AND is_full_tank = 1 AND odometer < ? AND id != ?
    ORDER BY odometer DESC LIMIT 1;
   ```
   Важно: «предыдущий» — это полный бак с наибольшим пробегом **строго
   меньше** пробега текущей записи, а не глобально последний по пробегу
   (так было раньше в удалённой `getLastFullTankEntry()` — она ломалась на
   записи, вставленной не по порядку, см. раздел 8). `excludeId` — запись
   не ищет сама себя как своего предшественника (важно при пересчёте: сама
   запись уже есть в таблице). Если подходящей записи нет (это первый
   полный бак в истории) — `consumption = null`.
3. `distance = entry.odometer − prev.odometer > 0`. Если пробег не вырос
   (ошибка ввода, дубликат) — `consumption = null`.

### Точная формула

```
partialLiters = SUM(liters) по всем заправкам с is_full_tank = 0,
                строго между prev.odometer и entry.odometer
                (sumPartialLitersBetween, fuel.ts)

totalLiters   = entry.liters + partialLiters
distance      = entry.odometer − prev.odometer
consumption   = round((totalLiters / distance) * 100, 2)   // calcConsumption()
```

Это **не** упрощённая формула из `ТЗ_приложение_авто_финал.md §6.2`
(`consumption = liters / пройдено × 100`, то есть только литры самого
полного бака) — код считает полную формулу, включая литры всех неполных
заправок, «накопленных» между двумя полными. См. список несоответствий
в конце файла, пункт 1.

Неполные заправки **сами по себе** `consumption` никогда не получают —
их литры участвуют только в числителе следующего полного бака.

### Пример: полный → 3 неполных → полный

| # | odometer | liters | is_full_tank |
|---|---|---|---|
| 1 | 10000 | 40 | 1 (полный) |
| 2 | 10300 | 15 | 0 |
| 3 | 10550 | 12 | 0 |
| 4 | 10800 | 10 | 0 |
| 5 | 11000 | 38 | 1 (полный) |

- Заправка **1**: предыдущего полного бака нет (это первая запись вообще)
  → `consumption = null`.
- Заправки **2, 3, 4**: `is_full_tank = 0` → `consumption = null` у каждой,
  всегда, независимо от соседей.
- Заправка **5**:
  - `prev = запись 1` (единственный полный бак с меньшим пробегом).
  - `distance = 11000 − 10000 = 1000`.
  - `partialLiters = 15 + 12 + 10 = 37` (все неполные строго между 10000 и 11000).
  - `totalLiters = 38 + 37 = 75`.
  - `consumption = 75 / 1000 × 100 = 7.5` л/100км.

Если бы заправка 2 (15 л) была отмечена `is_full_tank = 1`, она стала бы
новым «предыдущим полным баком» для заправки 5, и 37 л из примера выше
пересчитались бы совсем иначе (12+10=22, другая дистанция). Проверено
скриптом `scripts/verify_fuel_consumption.mjs` (сценарий 2): после такой
правки `consumption` и у 10300, и у 11000 автоматически пересчитываются на
верные значения (5.0 и 8.57 соответственно) — руками ничего поправлять не
нужно.

### Пересчёт при редактировании/удалении/импорте

`updateFuelEntry()` и `deleteFuelEntry()` (`fuel.ts`) вызывают
`recalcAllFullTankConsumption()` сразу после своего изменения. Правка
`liters`/`odometer`/`is_full_tank` у любой записи, а также удаление записи,
автоматически пересчитывает `consumption` у всех полных баков машины — не
только у затронутой записи, но и у соседей, на которых повлияла правка
(см. пример выше и сценарии 2-4 в `scripts/verify_fuel_consumption.mjs`).
То же самое — после `importDatabase()` (`db/backup.ts`, раздел 7). Отдельный
разовый вызов после сидирования исторических данных (`app/_layout.tsx`)
убран как избыточный: `addFuelEntry()` теперь сам пересчитывает всё при
каждой вставке.

## 2. Средний / минимальный / максимальный расход

### 2.0. «Сегмент» и средневзвешенный расход — общее понятие

**Код:** `db/repositories/fuel.ts` — типы `FuelSegment`, функции
`getFuelSegments()` и `calcWeightedConsumption()`.

Средний расход везде в приложении (дашборд, Stats) считается **не** как
простое среднее арифметическое `consumption` каждой заправки — такое
среднее даёт заправке на 50 км такой же вес, как заправке на 600 км, и один
короткий сегмент-выброс способен утащить итоговую цифру заметно выше
реальности (см. раздел 8, демонстрация — сценарий 6 в
`scripts/verify_fuel_consumption.mjs`).

Вместо этого вся история машины разбита на **сегменты** —
`getFuelSegments(carId)` возвращает по одному сегменту на каждый полный бак,
у которого есть предыдущий полный (ровно те баки, у которых непустой
`consumption`, раздел 1). Сегмент хранит:
```ts
type FuelSegment = {
  fullTankId:  number;
  date:        string;   // дата закрывающего полного бака (= d2) — по ней сегмент относят к периоду
  d1: string; o1: number;  // дата/одометр предыдущего (открывающего) полного бака
  d2: string; o2: number;  // дата/одометр закрывающего полного бака (= date/odometer текущего)
  liters:      number;   // литры этого полного бака + накопленные неполные между ним и предыдущим
  km:          number;   // distance между двумя полными
  consumption: number;   // calcConsumption(...) для этого сегмента, тот же, что хранится в БД
};
```
`d1/o1/d2/o2` существуют ради раздела 2.2 (разбивка расхода по месяцам) — не
трогают средневзвешенный расчёт этого раздела, который как и раньше относит
сегмент к периоду по одной дате `date` (= `d2`).
`calcWeightedConsumption(segments)` = `sum(segment.liters) / sum(segment.km) * 100`,
округление до 2 знаков; пустой список или суммарный `km <= 0` → `null`
(«—»). Эта единственная функция используется везде, где нужен средний
расход за период — ни дашборд, ни Stats не содержат собственной копии
формулы.

`recalcAllFullTankConsumption()` (раздел 1) теперь сама построена на
`getFuelSegments()` — цикл «для каждого полного бака найти предыдущий и
посчитать расход» существует только в одном месте.

### 2.1. Дашборд, карточка «Средний расход»

**Код:** `app/(tabs)/index.tsx` (блок `loadData`, использует `fuelRepo.getFuelSegments()`).

```js
avgConsValue = fuelRepo.calcWeightedConsumption(segments);
```

- Период: **вся история** машины — `segments` строятся по всем заправкам
  без ограничения по месяцам.
- Способ: средневзвешенный (раздел 2.0), не простое среднее.
- Если `avgConsValue === null` (сегментов пока нет), экран показывает
  подсказку вместо числа (`consReason`): `'noFullTank'`, если вообще нет ни
  одного полного бака, иначе `'needSecond'` (есть один полный, ждём
  второй — сегмент невозможен без пары).
- Карточка открывает модалку деталей (`consDetail`):
  - `best`/`worst`/`last5` — **по отдельным заправкам** (`Math.min`/`Math.max`
    по `consumption` каждого полного бака и 5 последних баков), не
    переведены на сегменты намеренно: смысл этих чисел — «лучшая/худшая
    отдельная заправка», а не взвешенный период;
  - `trend` — сравнение средневзвешенного текущего календарного месяца с
    средневзвешенным предыдущего: `calcWeightedConsumption(segments
    отфильтрованные по date.startsWith(ym/prevYM))`. Сегмент относится к
    месяцу по дате **закрывающего** его полного бака — так же, как сам
    `consumption`.

### 2.2. Stats → вкладка «Расход л/100»

**Код:** `buildConsStats()` и `aggConsumption()` в `app/(tabs)/explore.tsx`;
разбивка сегментов по месяцам — `splitSegmentByMonth()`,
`getOdometerWaypointsBetween()` и `getMonthlyFuelConsumption()` в
`db/repositories/fuel.ts`.

**Значение каждого столбика графика (по месяцам) — не относит сегмент
целиком к месяцу закрывающей заправки** (раньше было так, и это был баг:
длинный сегмент без полного бака внутри целиком уходил в один месяц, а
месяцы без полной заправки оставались пустыми — например отрезок
26.04→29.06 весь приписывался июню, а май показывал «—»). Теперь каждый
сегмент раскладывается по месяцам, которые он пересекает, пропорционально
пробегу:

```js
// getMonthlyFuelConsumption(carId) — один раз на весь экран (useFocusEffect),
// не на каждый рендер:
for (const seg of segments) {
  const waypoints = await getOdometerWaypointsBetween(carId, seg.o1, seg.o2);
  for (const { ym, km, liters } of splitSegmentByMonth(seg, waypoints)) {
    monthly[ym].km     += km;      // пробег сегмента, пришедшийся на этот месяц
    monthly[ym].liters += liters;  // литры в той же пропорции km(ym) / seg.km
  }
}

// splitSegmentByMonth(segment, waypoints) — для каждого месяца между d1 и d2:
odoStart = interpOdometerAtDate(points, monthStart);  // интерполяция по датам
odoEnd   = interpOdometerAtDate(points, monthEnd);    // points = [d1/o1, ...waypoints, d2/o2]
km(ym)     = odoEnd - odoStart;
liters(ym) = km(ym) / segment.km * segment.liters;

// aggConsumption(monthly, months) — значение столбика месяца:
r[ym] = (monthly[ym].liters / monthly[ym].km) * 100;   // «—» если km <= 0 (нет закрытого отрезка)
```

`waypoints` — все точки с известным одометром строго внутри сегмента
(неполные заправки + расходы с указанным пробегом), по датам между ними
(и концами сегмента `d1`/`d2`) строится кусочно-линейная интерполяция
одометра; чем их больше, тем точнее граница месяца внутри сегмента. Без
промежуточных точек интерполяция идёт прямо между `o1` и `o2`.

Важное свойство (проверено сценариями 7 и 8 `scripts/verify_fuel_consumption.mjs`):
сумма `km(ym)`/`liters(ym)` по всем месяцам, которые сегмент пересекает,
равна `segment.km`/`segment.liters` — разбивка ничего не теряет и не
добавляет, только распределяет.

**`buildConsStats()` (`explore.tsx:211-268`) — карточки под графиком
(avg/distance/min/max) — ветвится по `allTime`, а не считает всегда за весь
`months`:**

```js
// buildConsStats(fuel, segments, months, monthlyCons, selectedYM, allTime)
if (allTime) {
  // как раньше: целый сегмент относится к периоду по дате закрывающего бака
  periodSegments = segments.filter(s => months.includes(s.date.slice(0, 7)));
  avg      = fuelRepo.calcWeightedConsumption(periodSegments);  // средневзвешенно
  distance = Math.max(...odos) - Math.min(...odos);              // одометр всех заправок periodFuel
  min = Math.min(...cons); max = Math.max(...cons);               // по отдельным заправкам
} else {
  // режим месяца: та же доля, что в консМар шапки/графика, не весь months
  const m  = monthlyCons.get(selectedYM);
  avg      = m && m.km > 0 ? (m.liters / m.km) * 100 : 0;         // = consMap[selectedYM]
  distance = m?.km ?? 0;                                          // «Пробег за месяц»

  // min/max: сначала заправки, ЗАКРЫВШИЕСЯ в этом месяце (как и раньше).
  monthCons = fuel.filter(f => f.date.slice(0,7) === selectedYM && f.is_full_tank === 1 …);
  // Нет такой (monthCons пуст — например май: все заправки частичные,
  // месяц целиком «внутри» отрезка, который закроется позже) → фоллбэк на
  // отрезки, диапазон [d1,d2] которых ПЕРЕСЕКАЕТ месяц, целиком:
  segCons = monthCons.length > 0
    ? monthCons
    : segments.filter(s => s.d1.slice(0,7) <= selectedYM && selectedYM <= s.d2.slice(0,7))
              .map(s => s.consumption);
  min = Math.min(...segCons); max = Math.max(...segCons);    // «—», если segCons пуст
}
```

- Период: `allTime` ветка использует `months` = `MONTHS` (см. раздел 5) —
  последние 6 месяцев окна или все месяцы с данными. Ветка месяца игнорирует
  `MONTHS` целиком (окно — только навигация по графику) и всегда считает
  ровно за `selectedYM`.
- `min`/`max` в режиме месяца: сначала по отдельным заправкам, закрывшимся в
  `selectedYM` (как и раньше) — поведение для таких месяцев не менялось. Если
  в месяце нет ни одной закрывшейся полной заправки, вместо `0`/«—» теперь
  берётся `consumption` отрезков (`FuelSegment`), чей диапазон `[d1, d2]`
  пересекает `selectedYM` — целиком (`liters/km × 100` всего отрезка, а не
  доля месяца, в отличие от `avg`/`distance`). Один пересекающий отрезок →
  `min === max`; несколько — минимальный и максимальный среди них. «—»
  остаётся только когда и этот список пуст (в месяце вообще нет пробега —
  ни закрытой заправки, ни пересекающего отрезка). Проверено сценарием 8
  `scripts/verify_fuel_consumption.mjs` (`monthMinMax()`): май на
  `car_backup_Latest_v4.json` даёт `min === max === 5.97` — единственный
  отрезок 26.04→29.06 пересекает май целиком.
- `avg`/`distance` в режиме месяца намеренно читают ту же карту
  `monthlyCons` (`fuelRepo.getMonthlyFuelConsumption()`), что и
  `aggConsumption()` для столбика графика — поэтому число в карточке
  «Средний расход» и число в шапке над графиком для выбранного месяца
  гарантированно совпадают (одна и та же пара `{liters, km}`).
- `avg`/`distance` в режиме «за всё время», и цифра на дашборде (вся
  история), продолжают считаться по целым сегментам, как и раньше, —
  поведение `allTime`-ветки не менялось этой правкой.
- Месяц, в котором ни один сегмент не закрылся И не пересекает его (например
  последний отрезок после самой свежей полной заправки — она ещё не закрыта
  следующей), получает `km = 0` → «—» в UI, с подсказкой
  `stats.noClosedSegmentHint` («Нет закрытого отрезка между полными
  заправками»), показанной под заголовком суммы (`showNoSegmentHint` в
  `explore.tsx`).
- `distance` (и «Пробег за период» в `allTime`) выводится через `fmtKm()`
  (`explore.tsx`) — `Math.round()` до целых км + `toLocaleString()` для
  разделителя тысяч, например «1,285 км». Без явного `round()`
  `toLocaleString()` печатает дробную часть значения из
  `getMonthlyFuelConsumption()` (до 3 знаков по умолчанию — был баг,
  «1,284.774 км»); сами значения в `monthlyCons`/`splitSegmentByMonth`
  остаются дробными, округление только на выводе.

**Подпись периода под «Средним расходом»** (`metricSub`, `explore.tsx` рядом
с карточкой `cons-avg`): `t('stats.periodAllTime')` («за всё время») либо
`t('stats.periodLabel', { month: monthFullLower(selectedYM, locale) })` —
«за май 2026», ровно выбранный месяц (не диапазон окна из 6 столбиков).
Подпись карточки «Пробег за период»/«Пробег за месяц» (`metricDistance` /
`metricDistanceMonth`) переключается тем же `allTime`.

## 3. Одометр машины

**Функция:** `recalcCurrentOdometer()`, `db/repositories/cars.ts:62-89`.

```sql
UPDATE car SET current_odometer = (
  SELECT MAX(v) FROM (
    SELECT base_odometer                AS v FROM car            WHERE id = 1
    UNION ALL SELECT COALESCE(MAX(odometer), 0) FROM fuel_entry     WHERE car_id = 1
    UNION ALL SELECT COALESCE(MAX(odometer), 0) FROM expense        WHERE car_id = 1
    UNION ALL SELECT COALESCE(MAX(odometer), 0) FROM service_record WHERE car_id = 1
  )
) WHERE id = 1;
```

`current_odometer` — **не отдельное число**, а производная величина:
максимум из `car.base_odometer` (вводится в онбординге/настройках через
`setBaseOdometer()`, `cars.ts:33-38`) и максимального `odometer` среди
заправок, расходов и записей обслуживания. `expense.odometer` — nullable,
`COALESCE(..., 0)` исключает записи без пробега из максимума.

### Где вызывается

- `fuelRepo.addFuelEntry()` / `updateFuelEntry()` / `deleteFuelEntry()`
  (`db/repositories/fuel.ts`).
- `serviceRepo.addServiceRecord()` / `deleteServiceRecord()`
  (`db/repositories/services.ts:49, 76`).
- `carRepo.setBaseOdometer()` при ручном изменении базового пробега.
- `expenseRepo.addExpense()` / `updateExpense()` / `deleteExpense()`
  (`db/repositories/expenses.ts:46, 66, 79`) — уже вызывали пересчёт на
  момент проверки, отдельной правки не требовалось.
- `importDatabase()` (`db/backup.ts`) — после правки из этой задачи
  (раньше не вызывал, см. ниже).

После каждого пересчёта срабатывает колбэк `onRecalculated`
(`cars.ts:51-60`), зарегистрированный в `app/_layout.tsx` — он пересобирает
расписание push-уведомлений, потому что статусы регламентов зависят от
текущего пробега, а сами статусы нигде не хранятся.

**Важное свойство:** в отличие от старой модели (упомянутой в ТЗ, см.
несоответствия), пересчёт **двусторонний** — удаление записи с
максимальным пробегом опускает `current_odometer` обратно, а не оставляет
задранным. Нижняя граница — `base_odometer`, ниже него одометр никогда не
опустится, даже если все записи удалены.

### Что делает JSON-импорт с одометром

**Функция:** `importDatabase()`, `db/backup.ts`. После того как транзакция с
заливкой данных закоммичена, вызываются (вне транзакции, на уже
закоммиченных данных):
```js
await recalcCurrentOdometer();
await recalcAllFullTankConsumption();
```
Раньше ни то, ни другое не вызывалось — `current_odometer` брался из файла
как есть, а `consumption` заливался без проверки.

**`base_odometer`** внутри транзакции выставляется через
`resolveImportedBaseOdometer(backup)` (`db/backup.ts`), а не слепо равным
`backup.car.current_odometer`, как было раньше. Правило по приоритету:
1. В файле есть `car.base_odometer` (бэкап сделан после миграции v1→v2,
   когда это поле появилось в схеме) — берётся напрямую. Это именно то
   число, которое пользователь когда-то ввёл вручную.
2. Поля нет (старый формат бэкапа) — берётся **минимальный положительный
   `odometer`** среди всех заливаемых записей (`fuel_entry`, `expense` без
   `NULL`, `service_record`). Обоснование: слепо взять
   `current_odometer` из файла задрало бы нижнюю границу выше старых
   записей — при их последующем удалении одометр не мог бы опуститься
   ниже этой раздутой границы, хотя по факту машина когда-то прошла
   меньше. Минимальный пробег среди реально залитых записей — самая ранняя
   точка, которая действительно зафиксирована в истории.
3. Записей с пробегом нет вообще — единственное известное число это
   `current_odometer` из файла.

`current_odometer` в самой `UPDATE`-строке внутри транзакции по-прежнему
выставляется равным `backup.car.current_odometer` из файла — это лишь
начальное значение: `recalcCurrentOdometer()` сразу после транзакции
пересчитает его как `MAX(base_odometer, все odometer из только что
залитых записей)`, поэтому неточность в этой промежуточной строке не
критична. Если в залитых записях была большая цифра, чем
`backup.car.current_odometer` (устаревший/несогласованный файл), итоговый
одометр всё равно придёт к реальному максимуму, а не застынет на цифре из
файла. Проверено сценарием 5 в `scripts/verify_fuel_consumption.mjs`.

## 5. Статистика по месяцам (Stats)

**Код:** `app/(tabs)/explore.tsx`.

### Окно и навигация

- `MONTHS` (`explore.tsx:264-267`) — список месяцев `'YYYY-MM'`, по которым
  строятся все агрегаты вкладки. Два режима:
  - **окно**: `monthsWindow(windowEnd, 6)` (`explore.tsx:166-171`) — 6
    подряд идущих месяцев, заканчивающихся на `windowEnd`;
  - **за всё время**: `monthsWithData` — все месяцы, где есть хоть одна
    заправка или расход (вычисляется в `useFocusEffect`,
    `explore.tsx:286-289`, как `Set` дат `fuel_entry.date` ∪ `expense.date`,
    обрезанных до `'YYYY-MM'`).
- Стрелки `‹ ›` двигают `selectedYM` на ±1 месяц (`goMonth()`,
  `explore.tsx:311-320`). «Вперёд» блокируется на `selectedYM >= CURR_YM`
  (нельзя выбрать будущий месяц), «назад» — на `selectedYM <= earliestYM`
  (самый ранний месяц среди `monthsWithData`; если данных вообще нет —
  предел совпадает с текущим месяцем, то есть «назад» недоступно).
  Окно `windowEnd` сдвигается минимально — только когда `selectedYM`
  выходит за его левый или правый край, не на каждое нажатие.
- Тап по столбику или подписи месяца — тот же `setSelectedYM(ym)`, что и у
  стрелок (`explore.tsx:748, 787`); сдвигать `windowEnd` не нужно — все
  столбики уже внутри текущего окна. `isSelected = !allTime && ym ===
  selectedYM` (`explore.tsx:938`) — акцентная подсветка столбика/подписи, та
  же, что у текущего месяца по умолчанию.
  - **Область нажатия = вся колонка**, не только видимая полоска бара:
    `barsArea.alignItems: 'stretch'` (было `'flex-end'`, `explore.tsx:1436`)
    растягивает каждый `barWrapper`-`TouchableOpacity` на всю высоту
    `CHART_H`, а не только на высоту содержимого (при `flex-end` пустой
    0-высотный бар был физически нечем нажать). Сам бар внутри всё равно
    прижат к низу колонки через `barWrapper.justifyContent: 'flex-end'` —
    визуально ничего не изменилось, изменилась только зона тапа.
  - **В режиме «За всё время» тап отключён**: `disabled={allTime}` на
    `TouchableOpacity` и бара, и подписи (`explore.tsx:951, 992`), подсветка
    тоже гасится (`!allTime &&` в условии `isSelected`) — выбранный, более
    простой вариант из двух предложенных в задаче (альтернатива — тап
    выбирал бы месяц и одновременно выключал «За всё время» обратно в режим
    окна на 6 месяцев, что требует согласовывать `windowEnd` и выглядит
    менее предсказуемо: непонятно, какое окно показать сразу после выбора
    месяца из многолетней истории).

### Что агрегируется и как

`aggFuel`, `aggExpenses`, `aggConsumption`, `aggMaxOdo`, `buildCatStats`
(`explore.tsx:150-330`) принимают `MONTHS` как параметр и не знают, окно это
или «всё время» — это столбики ГРАФИКА и разбивка по категориям, они
считаются по окну из 6 месяцев (или по всем месяцам в `allTime`) и этой
правкой не менялись.

**Карточки под графиком — наоборот, знают про режим явно**:
`buildConsStats(fuel, segments, months, monthlyCons, selectedYM, allTime)`
(`explore.tsx:211-268`) и `buildExpStats(expenses, expMap, months,
selectedYM, allTime)` (`explore.tsx:279-304`) принимают и `MONTHS`, и
`selectedYM`, и `allTime` — и считают либо по всему `months` (`allTime`),
либо строго по `selectedYM` (режим месяца), см. раздел 2.2 для
`buildConsStats`. `buildExpStats` аналогично: «за всё время» сравнивает
МЕСЯЦЫ периода между собой (средний/мин/макс МЕСЯЦ, как раньше), в режиме
месяца сравнивать месяцы не из чего — поэтому `avg`/`min`/`max` считаются по
ОТДЕЛЬНЫМ тратам внутри `selectedYM` (средний чек, минимальная/максимальная
трата), а подписи карточек (`expMetricAvgMonth` и соседние ключи i18n)
меняются вместе со смыслом. «Заправки» карточек 2×2 под графиком не имеет —
там сумма в шапке уже считалась за `selectedYM` и не менялась.

В режиме «за всё время»:
- «Топливо»/«Расходы»: заголовок над графиком показывает сумму **по всем**
  месяцам (`periodTotal`, `explore.tsx:751`), не по одному месяцу.
- «Расход л/100»: заголовок показывает `consStats.avg`, честно пересчитанный
  по всем полным бакам всех месяцев с данными (не сумму и не среднее
  помесячных средних — см. раздел 2.2 про способ усреднения).
- Тренд к предыдущему месяцу и «км за месяц» скрыты — в all-time они не
  имеют смысла (`showTrend`/`monthKm`, `explore.tsx:771, 780`).
- График переходит на горизонтальный `ScrollView` с столбиками фиксированной
  ширины (`BAR_COL_W = 44`), а не фиксированные 6 колонок flex — потому что
  число месяцев может быть любым.
- Разбивка «По категориям» (`buildCatStats`) и donut «Доля трат по месяцам»
  считаются по тому же `MONTHS` — то есть по всей истории, а не по
  последним 6 месяцам.

## 6. Регламенты (reminders)

**Вкладка в таб-баре называется «Напоминания»/«Reminders»** (`nav.service` в
i18n), иконка — колокольчик `notifications-outline` (`app/(tabs)/_layout.tsx`).
Маршрут и имя файла (`app/(tabs)/service.tsx`) не переименовывались — меняется
только видимый текст/иконка, чтобы не трогать навигацию. Заголовок самого
экрана (`service.title`) переименован туда же. Builtin-категория расходов
`category.key = 'service'` («Сервис»/«Service», `db/database.ts`) — отдельная
сущность, её название НЕ менялось.

### Статус

**Функция:** `calcReminderRow()`, `utils/reminders.ts:26-50`.

```
mileage: used = currentOdo − last_odometer
         remaining = (last_odometer + interval_km) − currentOdo
time:    remaining = ceil((last_date + interval_days − сегодня) / 1 день)
статус: remaining <= 0 → due; remaining <= warn_before → soon; иначе ok
```
Статус **нигде не хранится** — пересчитывается на лету из `last_odometer` /
`last_date` + текущего пробега/даты при каждом рендере экрана и при каждом
планировании уведомлений.

### last_odometer / last_date — производные, не вводятся руками

**Функция:** `syncReminderFromRecords()`, `db/repositories/reminders.ts:82-108`.

При добавлении записи `SERVICE_RECORD` с заполненным `reminder_id`
(`serviceRepo.addServiceRecord()`, `services.ts:30-51`) и при удалении такой
записи (`deleteServiceRecord()`, `services.ts:60-76`) вызывается
`syncReminderFromRecords(reminderId)`:
```sql
SELECT odometer, date FROM service_record
 WHERE reminder_id = ? ORDER BY date DESC, odometer DESC, id DESC LIMIT 1;
```
Если такая запись нашлась — `last_odometer`/`last_date` регламента
становятся её значениями. Если не нашлась (все записи этого регламента
удалены) — откат на `start_odometer`/`start_date` (точка отсчёта регламента,
`reminder.start_*` в схеме, может быть как датой создания, так и прошлой
точкой, заданной вручную в форме — см. ниже). Таким образом **удаление**
последней закрывающей записи честно откатывает регламент, а не оставляет
его «выполненным».

`ORDER BY date DESC` — «последняя» запись определяется по **самой позднёй
дате**, а не по наибольшему пробегу: можно задним числом добавить запись с
пробегом меньше уже существующей, но более позднюю по дате, и именно она
станет «последней».

**Форма «Сделано» (`components/MarkDoneSheet.tsx`) допускает пробег МЕНЬШЕ
`car.current_odometer`.** Раньше `handleSave()` отклонял такое значение
(`parsedOdo < car.current_odometer → common.errorOdometer`), что не давало
зафиксировать реальную прошлую работу (например, масло, замененное на
`206500` км при текущих `211294`). Проверка оставлена только на `>= 0` и
корректность числа (`service.odoInvalid`); дата и пробег остаются
обязательными, дата — не в будущем (`maximumDate` пикера). Пробег ниже
текущего не опускает `car.current_odometer`: `recalcCurrentOdometer()`
(раздел 3) берёт `MAX` по всем записям, а не присваивает значение из новой
записи напрямую.

**Форма «Расход» (`app/add-expense.tsx`) — тот же принцип.** `validate()`
раньше блокировал пробег ниже `car.current_odometer` только при добавлении
(`!isEdit`), что не давало внести расход задним числом (например, «Замена
масла» на `202007` км при текущих `211294`). Проверка приведена к единому
правилу: пустое значение допустимо, иначе — целое число `>= 0`
(`addExpense.errorOdometer`), без сравнения с текущим одометром, и теперь
действует одинаково при добавлении и редактировании. `odometer` в `expense`
и так `NULLable` (раздел 5.3), а `recalcCurrentOdometer()` берёт `MAX` по
всем записям — пробег ниже текущего никогда не уменьшит
`car.current_odometer`, в т.ч. при правке/удалении записи с максимальным
пробегом (проверено `scripts/verify_expenses.mjs`). Форма «Заправка»
(`add-fuel.tsx`) сохраняет свою отдельную проверку (`odoNum < currentOdometer`
при добавлении) — там монотонный пробег нужен для расчёта расхода топлива
между заправками (раздел 1), это сознательное исключение, не трогалось.

### Создание и редактирование регламента — «когда сделано в последний раз»

`addReminder()` (`reminders.ts`): если `start_odometer`/`start_date` не
переданы явно, берутся `start_odometer = текущий пробег машины` /
`start_date = сегодня`, и `last_* = start_*` — поведение по умолчанию не
изменилось (регламент стартует «в норме»).

Форма `app/add-reminder.tsx` теперь сама передаёт `start_date` (для
`type='time'` — поле «Когда сделано в последний раз»; для `type='mileage'` —
«Дата последней замены») и `start_odometer` для обоих типов. Для
`type='mileage'` поле «Пробег при последней замене» обязательно и
предзаполнено сегодня/текущим пробегом (если его не трогать — результат как
раньше), но можно указать и прошлую точку — например, замену масла,
сделанную до того, как завели регламент (`206500` км при текущих `211294`
км). Пробег валидируется диапазоном `0 ≤ значение ≤ current_odometer`
(`addReminder.errorLastOdo`) — нельзя указать замену в будущем по пробегу, но
можно в прошлом.

Для `type='time'` под полем даты есть второе поле — «Пробег при последнем
выполнении, км» (`addReminder.lastDoneTimeOdo`), **необязательное**: можно
оставить пустым (по умолчанию и пустое). Это чисто информационное поле —
`calcReminderRow()` для `type='time'` читает только `last_date`, `last_odometer`
не трогает (строка 401-404 выше). Пустое значение сохраняется в тот же
`start_odometer` как сентинел `NO_ODOMETER = -1` (`utils/reminders.ts`) —
колонка в SQLite остаётся `start_odometer INTEGER NOT NULL DEFAULT 0`
(`db/schema.ts`), миграция не понадобилась. В `ReminderDetailModal` и в
карточке регламента (`app/(tabs)/service.tsx`, функция `lastOdoInfoLabel()`)
сентинел отображается как «—» вместо числа. Как и `start_odometer` для
`type='mileage'`, значение переопределяется первой же `SERVICE_RECORD` по
регламенту через `syncReminderFromRecords()` — откат при удалении записи
работает одинаково для обоих типов.

При редактировании существующего регламента форма предзаполняет эти поля не
из `start_*` (который может быть «застывшим» значением от момента создания),
а из `last_date`/`last_odometer` — то, что фактически показано как «последний
раз» на экране. Сохраняет всё равно в `start_*`; `updateReminder()`
(`reminders.ts`) сразу после `UPDATE` вызывает `syncReminderFromRecords(id)`
— если у регламента уже есть хотя бы одна `SERVICE_RECORD`, `last_*`
пересчитаются из неё (правка `start_*` в этом случае ни на что не повлияет,
пока эта запись не будет удалена — откат, описанный выше, не ломается);
если записей ещё нет, `last_*` станут равны только что сохранённым `start_*`.

**`primeNotifiedStatus(id)`** (`reminders.ts`, вызывается в конце и
`addReminder()`, и `updateReminder()`): раньше регламент после создания
всегда был «в норме», и `notified_status` (по умолчанию пустой) совпадал с
реальным статусом — переходов не было, push не слался. Теперь регламент
может оказаться уже «скоро»/«пора» сразу после сохранения с прошлой датой.
Без этой функции ближайший `scheduleReminderNotifications()` увидел бы
`notified_status = null` против реального `due` и принял бы это за
УХУДШЕНИЕ — и немедленно прислал push, хотя пользователь только что сам
ввёл эти данные и уже видит статус на экране. `primeNotifiedStatus()`
пересчитывает статус через `calcReminderRow()` и сразу выставляет
`notified_status` в него (только для `type='mileage'` — только там это поле
имеет смысл), поэтому такой push не считается переходом и не отправляется;
отправится только о следующем, настоящем ухудшении.

### Push-уведомления — два разных механизма по типу

**Функция:** `scheduleReminderNotifications()` / `runSchedule()`,
`notifications/engine.ts:247-414`. Вызывается при каждом старте приложения
и после каждого пересчёта одометра (через слушатель `onRecalculated`).
Вызовы сериализованы через `_queue` (`engine.ts:126, 250`), чтобы два
параллельных пересчёта не отправили дублирующийся push.

**`type = 'time'`** — календарный триггер `SchedulableTriggerInputTypes.CALENDAR`
на 9:00 по времени телефона (`engine.ts:348-409`):
- `ok` → разовый триггер на `warnDate` (дата срабатывания «скоро»);
- `soon` → разовый триггер на `dueDate`;
- `due` → повторяющийся (`repeats: true`) каждый день в 9:00, текст
  пересчитывается только при следующем планировании, не в реальном времени.
- Если вычисленный момент уже прошёл сегодня — переносится на завтра
  (`at9AMOrLater()`/`next9AM()`, `engine.ts:90-105`).

**`type = 'mileage'`** — событийная модель, **без** CALENDAR и **без**
повтора (`engine.ts:315-343`): пробег сам не растёт между записями
пользователя, значит ждать 9:00 бессмысленно.
- Сравнивается текущий статус с `reminder.notified_status` (поле в схеме,
  `'soon' | 'due' | null`).
- Стало хуже (`STATUS_ORDER[status] < STATUS_ORDER[notified]`) → немедленный
  push (`trigger: null`) **один раз** на переход, `notified_status`
  обновляется на новый статус.
- Стало лучше (в т.ч. после «Сделано» или удаления записи, откатившей
  регламент) → push не шлётся, `notified_status` тихо сбрасывается
  (`null`, если вернулись в `ok`), чтобы следующее ухудшение уведомило снова.
- Текст просрочки — отдельные ключи `overdueKm`/`overdueDays`
  (`overdueBody()`, `engine.ts:113-123`); ровно `remaining === 0` — это
  «срок сегодня» (`notifications.due`), не «просрочено на 0».

## 7. Импорт и экспорт JSON

**Файл:** `db/backup.ts`. Формат: `{ version: 1, exportDate, car, settings,
categories, reminders, fuelEntries, expenses, serviceRecords }`.

### Экспорт (`exportDatabase()`, `backup.ts:50-115`)

Читает все 7 таблиц целиком, сериализует как есть в JSON (без
преобразований), сохраняет через SAF (Android) или системный Share
(iOS/фоллбэк).

### Импорт (`importDatabase()`, `backup.ts:159-327`)

1. Валидирует только структуру: `version === 1` и что `categories`,
   `reminders`, `fuelEntries`, `expenses`, `serviceRecords` — массивы.
   Содержимое полей (типы, диапазоны, непротиворечивость) **не проверяется**.
2. В одной транзакции (`withExclusiveTransactionAsync`, откат при ошибке):
   - удаляет все строки `service_record`, `expense`, `fuel_entry`,
     `reminder`, `category`;
   - `car`/`app_settings` не удаляются — обновляются `UPDATE` по `id = 1`
     (строки созданы при первой инициализации БД и всегда существуют);
   - категории, регламенты, заправки, расходы, записи обслуживания —
     вставляются **с оригинальными `id` из файла** (`INSERT` явно указывает
     `id`), чтобы сохранить связи по `reminder_id`/`category_id`;
   - `app_settings.onboarding_completed` принудительно ставится в `1`
     (раз есть что импортировать — значит онбординг не нужен);
   - `sqlite_sequence` (автоинкремент) подгоняется под `MAX(id)` каждой
     таблицы, если таблица существует.
3. Берётся **как есть, без пересчёта** — только это:
   - `fuel_entry.price_per_liter` — из файла, напрямую. Это сознательное
     решение, не упущение: это просто `total_cost / liters` за заправку,
     пересчитывать его не из чего, кроме тех же чисел из того же файла;
   - `reminder.start_odometer`/`start_date` — если в файле их нет (старый
     формат бэкапа без этих колонок), подставляются текущие
     `last_odometer`/`last_date` (`backup.ts`).
4. Пересчитывается **автоматически после импорта** (вне транзакции, сразу
   после коммита — раздел 3 и раздел 1 этого документа):
   - `car.base_odometer`/`current_odometer` — `resolveImportedBaseOdometer()`
     + `recalcCurrentOdometer()`;
   - `fuel_entry.consumption` у всех полных баков — `recalcAllFullTankConsumption()`.
   До этой правки ни одно из двух не пересчитывалось: одометр и расход
   брались из файла как есть, и несогласованность (например, после ручной
   правки файла) обнаруживалась не сразу, а только при следующем
   добавлении/редактировании записи.

Отдельно — `db/legacy-import.ts: importLegacyData()`: это **не** та же
функция, что импорт бэкапа пользователя. Это захардкоженный личный набор
исторических заправок/расходов автора приложения (`FUEL_SEEDS`,
`EXPENSE_SEEDS`), который заливается через настоящий `addFuelEntry()`
(с пересчётом цены и расхода) **на каждом запуске**, но только когда
`APP_VARIANT === 'data'` (`app/_layout.tsx:166-171`); дедуп — по совпадению
даты+пробега+суммы. Сборка `.clean` (`APP_VARIANT === 'clean'`) этот код
не выполняет вообще.

## 8. Известные особенности и риски

- **Флаг «полный бак» — единственный источник правды для расхода.**
  Если пользователь ошибся (отметил неполную заправку как полную, или
  наоборот) — расход всех заправок между соседними полными баками
  пересчитается неверно, и это не покажет никакой ошибки в интерфейсе,
  просто другое число. Поправить задним числом через обычное
  редактирование формы теперь **можно** — `updateFuelEntry()` сам
  пересчитывает `consumption` у всех полных баков машины (раздел 1) —
  но само число всё равно зависит от честности флага, приложение не умеет
  угадать, какая заправка была реально полной.
- **Первый полный бак в истории — всегда без расхода.** Это не баг, но
  выглядит как «пропавшие данные», если не знать формулу.
- **Выброс-сегмент на коротком пробеге всё равно немного искажает картину,
  хоть и меньше, чем раньше.** Средний расход (раздел 2.0) теперь
  средневзвешенный — короткий сегмент на 50 км не весит столько же, сколько
  обычный на 600 км (проверено сценарием 6 в
  `scripts/verify_fuel_consumption.mjs`: та же цифра, что раньше тянула
  простое среднее до 11.67, средневзвешенно даёт честные 7.93). Но
  `min`/`max` (раздел 2.2) по-прежнему берутся по отдельным заправкам без
  взвешивания — это сделано намеренно (смысл этих чисел — «лучшая/худшая
  заправка», а не период), но аномальная ОДНА заправка всё ещё может стать
  видимым «максимумом» карточки, даже если на средневзвешенный `avg` она
  почти не влияет.
- **Дашборд и Stats показывают разные периоды под похожими подписями.**
  «Средний расход» на дашборде — вся история; та же метрика на Stats —
  последние 6 месяцев или all-time, в зависимости от тумблера. Цифры
  закономерно расходятся.
- **Окно 6 месяцев и режим «за всё время» — на экране Stats, но НЕ влияют
  на дашборд.** Карточки Главной считают по-своему (раздел 2.1, 4.1),
  независимо от того, что выбрано на Stats.
- **Импорт JSON не пересчитывает `price_per_liter`.** Это сознательное
  решение (пункт 4 раздела 7), а не упущение — если файл бэкапа был
  отредактирован руками с неверной ценой за литр, импорт занесёт её как
  есть. `current_odometer`/`base_odometer` и `consumption`, в отличие от
  цены, теперь пересчитываются автоматически (разделы 1, 3, 7).
- **`recalcAllFullTankConsumption()` — O(n) запросов к БД на n полных
  баков.** Для личного использования (десятки–сотни заправок) это доли
  секунды; при каком-то экстремально большом количестве записей стоило бы
  переписать на одну SQL-агрегацию, но сейчас такой необходимости нет.
- **`notified_status` — не то же самое, что статус регламента.** Статус
  всегда актуален (пересчитывается на лету); `notified_status` — это
  отдельная «память» движка уведомлений о том, что уже показано. Если
  расписание не пересобиралось (например, уведомления были выключены, а
  потом включены на уже «due» регламенте) — `notified_status` может
  временно не совпадать с видимым статусом до следующего
  `scheduleReminderNotifications()`.
- **На Android `windowSoftInputMode="adjustResize"` (манифест, дефолт
  Expo-шаблона) сам по себе не поднимает поля над клавиатурой при
  `edgeToEdgeEnabled: true` (`app.config.js`).** Edge-to-edge рисует поверх
  системных баров, и `adjustResize` не ресайзит окно так, как раньше —
  клавиатуру нужно явно отрабатывать на стороне RN. Поэтому все формы с
  полями ввода (`add-fuel.tsx`, `add-expense.tsx`, `add-reminder.tsx`,
  `MarkDoneSheet.tsx`, модалки в `settings.tsx`) оборачиваются в
  `KeyboardAvoidingView` с `behavior: 'height'` на Android (и `'padding'` на
  iOS) — константа `KEYBOARD_AVOIDING_BEHAVIOR` в
  `hooks/use-keyboard-aware-scroll.ts`. До этой правки часть экранов
  (`add-fuel.tsx`, `add-expense.tsx`, `add-reminder.tsx`) передавала
  `behavior: undefined` на Android, то есть не делала вообще ничего — именно
  это и было видимым багом («поле и кнопка „Сохранить“ под клавиатурой»).
- **Автопрокрутка сфокусированного поля — через
  `ScrollView.scrollResponderScrollNativeHandleToKeyboard()`, а не через
  стороннюю библиотеку.** Этот метод жив в RN 0.81 (часть
  `ScrollResponderMixin`) и десятилетиями используется в «keyboard aware
  scroll view»-библиотеках; `useKeyboardAwareScroll()` оборачивает его в
  хук, который даёт `scrollRef` (на `ScrollView`) и `onFieldFocus` (вызывать
  из `onFocus` каждого `TextInput`). `automaticallyAdjustKeyboardInsets` у
  `ScrollView` сюда не подошёл — это iOS-only проп, на Android не работает.
- **Иконка строки расхода в списках — из категории, а не общая.**
  `resolveExpenseIcon(category?.icon)` (`utils/icons.ts`) — тонкая обёртка
  над уже существующим `resolveIcon()` (тот же маппинг Tabler→Ionicons, что
  и на плитках категорий в `add-expense.tsx`/`categories.tsx`/Stats
  `app/(tabs)/explore.tsx`, один набор иконок, не продублирован). Запасная
  иконка `EXPENSE_FALLBACK_ICON = 'receipt-outline'` — когда категория
  удалена (`category_id` не находится в `catMap`) или у неё пустая `icon`.
  Подключено в трёх местах, где строился расход с общей иконкой-чеком:
  `components/HistoryList.tsx`, `app/(tabs)/index.tsx` (`recentDisplay()`),
  `components/RecordDetailModal.tsx`. Фон/акцентный цвет строки расхода
  (`colors.iconBgExpense` / `colors.statusSoon.text`) не менялись — меняется
  только сама иконка. Категории везде загружаются один раз (`catMap`), новых
  запросов на строку не добавилось. Экран Stats (`app/(tabs)/explore.tsx`)
  уже показывал иконку категории (`ionName(cat.icon)` на столбиках
  «По категориям» и в модалке категории) и правки не требовал — список
  отдельных записей внутри модалки категории своих иконок не рисует вообще
  (только дата/сумма/описание).

## Несоответствия между `docs/ТЗ_приложение_авто_финал.md` и кодом

Только список, без исправлений — по заданию.

1. **§6.2** ТЗ описывает упрощённую формулу расхода (`consumption = liters /
   пройдено × 100`, то есть только литры самого полного бака) и явно
   помечает её как стартовый вариант («На старте можно упростить»). Код
   реализует полную формулу: числитель = литры полного бака + литры всех
   неполных заправок между двумя полными (`sumPartialLitersBetween`).
   ТЗ не обновлён под фактическую реализацию.
2. **§5.1** Таблица `CAR` в ТЗ не содержит поля `base_odometer` — только
   `current_odometer` с описанием «обновляется автоматически: при любой
   новой записи с бóльшим пробегом это поле подтягивает новое значение»
   (то есть односторонний рост). Код (`recalcCurrentOdometer()`) ведёт
   себя иначе: двусторонний пересчёт как максимум из `base_odometer` и
   всех записей, который может и опускать одометр при удалении записи
   с максимальным пробегом.
3. **§5.6** Таблица `REMINDER` в ТЗ не содержит полей `start_odometer`,
   `start_date`, `notified_status` — все три есть в реальной схеме
   (`db/schema.ts`) и участвуют в логике откатов и дедупликации push.
4. **§6.3** «При нажатии «Сделано»: в регламенте обновляются
   `last_odometer` и `last_date` на текущие» — формулировка подразумевает,
   что поля обновляются напрямую и автоматически текущими значениями.
   В коде `last_odometer`/`last_date` — производные от записей
   `SERVICE_RECORD` (которые пользователь вводит вручную, дата и пробег
   обязательны, не обязательно «текущие»), пересчитываемые
   `syncReminderFromRecords()`, с откатом на `start_*` при удалении записи.
   Этот механизм откатов в ТЗ вообще не описан.
5. **§6.3** ТЗ описывает единую модель push для обоих типов регламента:
   «`mileage soon/due` → повторяющийся CALENDAR каждый день в 9:00».
   Код реализует для `type = 'mileage'` принципиально другую, событийную
   модель: немедленный `trigger: null` push один раз на переход статуса,
   без какого-либо CALENDAR-триггера и без ежедневного повтора. Модель
   «ежедневно в 9:00» в ТЗ сохранена только для `type = 'time'`.
6. **§6.3** Текст просроченного `time`-регламента в ТЗ не разделён по
   типу; код использует отдельные ключи `overdueKm`/`overdueDays`, и
   отдельно обрабатывает `remaining === 0` как «срок сегодня»
   (`notifications.due`), а не как «просрочено на 0 дней/км».
7. **§4.5 / раздел статистики** ТЗ описывает экран статистики на уровне
   «графики», без деталей. Окно 6 месяцев, навигация стрелками и режим
   «за всё время» (раздел 5 этого документа) — более поздняя функциональность,
   не отражённая и не противоречащая ТЗ напрямую, просто не описана.
8. **§9** ТЗ допускает формат бэкапа «JSON или CSV». Реализован только
   JSON — не противоречие по существу (выбор одного из двух предложенных
   вариантов), но стоит иметь в виду, что CSV не реализован.
